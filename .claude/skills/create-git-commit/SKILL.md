# Git コミット作成ガイド

## コミット / プッシュの実行ポリシー

`git commit` と `git push` は **明示的な依頼があったときだけ実行する**。実行してよいかの判定はこの節だけで行う。

- 「コミットして」「コミットと PR の作成をお願い」のように、依頼に実行が含まれている場合、**その依頼自体が許可である**。「コミットしてよいですか」と確認し直すと依頼の完了が 1 往復遅れるだけなので、後述の「コミット時に提示すること」を示してそのまま実行する
- PR 作成の依頼は、その前提となるコミットとプッシュの依頼を含む。前提を欠いたまま PR は作成できないため
- 依頼が無い間は実行しない
- 依頼はその作業に限る。別の作業に移ったら、改めて依頼を受けてから実行する
- 「コミットできる状態か確認したい」という文脈では、`git status` と `git diff --stat` の結果を示すに留め、コミットは実行しない

## 禁止する操作

明示的な要請がない限り実行しない。

- `git push --force` / `git reset --hard` / `git clean -f` などの破壊的操作
- `main` ブランチへの直接コミット。Issue ごとに `feature/issue<番号>` のようなブランチを切る
- `--no-verify` によるフックのスキップ。フックが失敗したら原因を直してから commit し直す
- `--amend` による既存コミットの書き換え。直すときは新しいコミットを作る

## メッセージの構成

```
<変更内容を端的に表す日本語>

<本文: なぜその変更が必要だったか>
```

### 表題

- 日本語で、その変更が何をするものかを 1 行で書く
- 「〜する」の形にする（例: `公式カード検索の参照手順書を追加する`）
- Issue 番号は付けない。ブランチ名と PR が Issue と紐づいており、コミット表題に重ねる必要がない

### 本文

**何を変えたかは差分が語る。なぜ変えたかは差分から読めない。** 本文には後者を書く。

- 表題との間に空行を挟む
- なぜその変更が必要だったか、どういう問題を解決するかを書く
- 設計判断をしたなら、選んだ案と選ばなかった案、その理由を書く
- 制約や妥協には出典（Issue 番号・ドキュメントの URL・実測結果）を添える
- **検討したうえで変更しなかったこと**があれば書く。次に読む人が同じ検討をやり直さずに済む
- 論点が複数あるときは箇条書きにしてよい

理由が自明な変更（typo の修正、依存パッケージの更新など）では本文を省いてよい。迷ったら書く。

書き分けの原則として、コードには How、テストコードには What、コミットログには Why、コードコメントには Why not を置く。

### 記載例

```
デッキ検証を公式ツールのレギュレーションチェックに寄せる

デッキ枚数や同名カードの制限を自前のコードで判定する案もあったが、
判定ルールの改定に追従し続けるコストが高い。公式デッキ構築ツールの
レギュレーションチェックが同じ判定を提供しているため、検証はそちらに
任せ、このリポジトリでは参照手順の文書化に徹する。

https://www.pokemon-card.com/deck/deck.html
```

## ステージング

`git add` の前に `git status --short` で全件を確認し、意図しないファイルが含まれていないことを確かめる。認証情報や個人の設定ファイルが `.gitignore` の網から漏れていることがある。

1 つのコミットには関連する変更だけを含める。論点が異なる変更は別のコミットに分ける。ただし、分けると中間のコミットで検査が通らなくなる場合や、片方だけでは変更の理由が説明できない場合は、1 つにまとめてよい。まとめたときは、その理由をコミット本文に書く。

## コミット時に提示すること

コミットを実行するときは、報告に次を含める。実行の可否は上の実行ポリシーで判定済みなので、これは追加の許可取りではない。依頼を受けて実行する場合は、提示と実行を同じ応答の中で行い、返答を待たない。

1. ステージングしたファイルの一覧（`git status --short`）
2. 変更行数（`git diff --cached --stat`）
3. コミットメッセージ本文

想定外のファイルが入っていないか、メッセージが文脈を保っているかを、その場で検証して修正を依頼できるようにするため。

## 実行例

```bash
git commit -F - <<'MSG'
<表題>

<本文>
MSG
```

`-F -` で標準入力から渡す。`-m` にヒアドキュメントを埋め込む方式は、本文にバッククォートが含まれるとシェルがコマンド置換として解釈するため使わない。
