# カードの記録を書く

カード 1 種について、計算の骨組み(`packages/solo-play-simulator`)が読むカードの記録を書く。記録は公式のカード詳細ページと公式 Q&A で確かめた事実だけで書き、記憶で書かない。用語は [GLOSSARY.md](../../../GLOSSARY.md)「デッキ診断」の節(効果の記法、効果の翻訳、場にある間ずっと働く効果、カードの記録、裁定のデータ、計算の前提)に従う。記法の部品、欄の識別子、検査の設計の理由は [docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md)「効果の記法と裁定のデータ」にある。

## いつ使うか

- 計算の骨組みが `MissingCardRecordsError`(記録の無いカード ID がある)を出したとき
- デッキを計算できるように、デッキの全カードの記録をそろえるとき
- 対戦風の一人回しのルールで、デッキの記録を見直すとき

- [docs/pokemon-tcg/site-usage-notes.md](../../../docs/pokemon-tcg/site-usage-notes.md)(転載しない、過度な連続アクセスをしない)
- [docs/pokemon-tcg/card-lookup.md](../../../docs/pokemon-tcg/card-lookup.md)(3 点確認、同じ名前のカードと印刷)
- [docs/pokemon-tcg/faq-lookup.md](../../../docs/pokemon-tcg/faq-lookup.md)(公式 Q&A の検索と出典の書き方)
- [docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md)「効果の記法と裁定のデータ」の「基本操作」の表、「欄と部品の識別子」、「部品を足す手順」、「カードによらない実行の決まり」
- 記法のスキーマ `packages/solo-play-simulator/src/card-record-schema.ts` と、同じ種類のカードの記録の例(`src/card-records/<種類>/`)

## 手順

### 1. デッキを読み、記録の無いカードを洗い出す

[docs/pokemon-tcg/deck-tool.md](../../../docs/pokemon-tcg/deck-tool.md) 手順 1 に従い、デッキコードから 60 枚の内容(カード名、カード ID、枚数)を読む。

カード ID ごとに、記録があるかを調べる。記録はどの印刷のカード ID からも引ける(`src/card-record-table.ts` の `cardRecordTable`)。

- 記録がある: そのカード ID が記録の `cardIds` にあれば、この手順では何もしない
- 同じ名前の記録はあるが、そのカード ID が `cardIds` に無い: 手順 3 で詳細ページを見比べ、カードテキストが同じなら `cardIds` に足す。違えば別のカードとして新しい記録を書く
- 記録が無い: 手順 2 から書く

### 2. 翻訳の状態を決める

棚卸しの一覧([docs/card-effect-inventory.md](../../../docs/card-effect-inventory.md))は Issue 27 の分類の記録で、今後は直さない。記録が正である。一覧に行が無いカードでも、一覧に行を足さない。

記録の翻訳の状態は、設計文書「カードの記録の形」の翻訳の状態の定義で決める。効果の翻訳があれば `translated`、記法で書けなければ `notTranslatable`、効果の翻訳が要らないもの(ダメージだけのワザしか持たないポケモン、効果を持たないカード)は `irrelevantToCalculation`(ワザのダメージは計算する)。

一覧の根拠を参考に読むのはよいが、根拠にある「〜と同じ形」「〜の操作で書ける」は、部品を選ぶ前に詳細ページで確かめる。ブースターex(048810)の根拠は「あふれるねがいと同じ形」だったが、実際は選んだ 1 匹にまとめてつける別の形だった。

### 3. 全カードの 3 点確認をする

[docs/pokemon-tcg/card-lookup.md](../../../docs/pokemon-tcg/card-lookup.md) に従い、記録を書くカードの詳細ページを開いて読み直す。前に読んだことがあっても、記録を書く日に読み直す(記録の `verifiedOn` はこの日)。スタンダードで使えるかは、カード名の完全一致で検索一覧の全ページを見て判定する。

詳細ページを読むときの注意:

- **見出し(`h2`)ごとに読むだけでは足りない。** ワザの欄の前の見出しの無い段落に、ベンチにいる間ワザのダメージを受けないルールの文がある(ドラパルトex 049264、イーブイex 049282)。これがあれば「テラスタル」のポケモンとして `isTerastal` を真にする。「特別なルール」の見出しの下の文で、ポケモンex(`pokemonEx`)かメガシンカex(`megaEvolutionEx`)かを決める
- **エネルギーのタイプはアイコンで書かれる。** ワザに必要なエネルギー、タイプ、ワザの文の中のエネルギー(「[炎]エネルギー」)は `<span class="icon-fire icon"></span>` のような空の要素で、HTML からテキストだけを抜くとタイプが消える。アイコンの class を文字に置き換えてから読む。`icon-none` は無色 1 個(記録では `colorless`)、`icon-void` は必要なエネルギー無し(空の並び)
- **にげるエネルギーは、にげる欄のアイコンの個数。** 欄が空なら 0
- **ダメージが空欄でも、効果の文でダメージを与えるワザがある**(プロージョンY、クルーエルアロー)。ダメージは効果の文の数値で持つ(下の「ワザのダメージ」)
- **進化の段階は進化マーク(たね、1進化、2進化)、進化前の名前は詳細ページの「進化」の欄から写す。** 欄は上の段ほど進化が進んだポケモンで、いちばん下の段が系統のたねポケモン。同じ段階のポケモンは 2 つずつ折り返して並ぶため、このカードの 1 つ下の段が進化前とは限らない(ヤドキング 045978 は、1 つ下の段がヤドキングex とメガヤドランex で、ヤドンはその下)。自身より下の段のうち、進化の段階が 1 つ前のポケモンを進化前にする。2進化ポケモンは系統のたねポケモンの名前も `basicPokemonOfEvolutionLine` に写す
- **詳細ページのデータに抜けがあることがある。** Nのゾロアークex 048634 の詳細ページには「特別なルール」の見出しが無いが、同じカードテキストのほかの印刷(047069、047237)にはある。属性が名前やほかの印刷と食い違うときは、ほかの印刷の詳細ページと見比べてから決め、決めたことを PR に書く

印刷の見比べ:

- **読んだ印刷が検索一覧に出ないことがある**(リザード 049481、メガリザードンYex 049482)。一覧に出る同じ名前の印刷の詳細ページと見比べ、カードテキストが同じ印刷を記録の `cardIds` に足す
- **同じ名前でもカードテキストが違えば別のカード**で、別の記録にする。見比べていなければ「印刷違い」と書かない(card-lookup.md 手順 8)
- 記録の `cardIds` の先頭は、この手順で詳細ページを読んだ印刷にする。ファイル名は先頭のカード ID になる

### 4. 裁定を確かめる

[docs/pokemon-tcg/faq-lookup.md](../../../docs/pokemon-tcg/faq-lookup.md) に従い、カード名、特性の名前、ワザの名前で公式 Q&A を検索する。カードテキストだけでは翻訳が決まらない点(使える条件、何枚まで選べるか、選ばなくてよいか、数え方、場にある間ずっと働く効果の範囲、ほかのカードとの組み合わせ)を探す。

- 翻訳が変わる点は、裁定のデータ(`rulings`)に論点、採った解釈、翻訳への反映、出典を書く。出典は検索結果の URL(`freeword` 付き)、該当した質問の要旨(自分の言葉で)、確認日の 3 点。Q&A の質問文と回答文は転載しない
- **公式 Q&A の関連カードは、記録に無い印刷のことがある。** 出典にするときは、その印刷の詳細ページを見比べ、カードテキストが同じなら記録の `cardIds` に足す
- **カードに直接の公式 Q&A が無い論点**は、同じ書き方の別のカードの Q&A を拠り所にし、出典を「該当なし」(`noMatchingQa`。検索語、拠り所、確認日)として残す(ミツルの思いやり、インフェルノX)。「該当なし」の裁定は計算の前提にプロジェクトの解釈として出る
- 骨組みがカードによらない決まりとして持つ点(最初の操作に対象が無ければ使えない、条件の付いた山札の検索は 0 枚でもよい、など。設計文書「カードによらない実行の決まり」)は、カードごとの裁定に書き写さない。そのカードの Q&A がその決まりと食い違うときは、記録ではなく骨組みの決まりを見直す

### 5. 記録を書く

置き場所は `packages/solo-play-simulator/src/card-records/<種類>/<先頭のカード ID>.json`。種類のディレクトリは `pokemon`、`goods`、`pokemon-tools`、`supporters`、`stadiums`、`energies`。先頭に `"$schema": "../card-record.schema.json"` を書く。欄と部品の識別子は設計文書「欄と部品の識別子」と、基本操作の表の「記法の識別子」の列にある。

- **カードテキストを引き写さない。** 記録に書く文(含めなかった効果の `description`、裁定の文)は、確認した事実を自分の言葉で書く
- **値の無い欄は `null` を書かず、欄ごと持たない。** たねポケモンは `evolvesFrom` を持たない。ポケモンex・メガシンカex でないポケモンは `exRule` を持たない。ダメージだけのワザと翻訳しない効果のワザは `effect` を持たない。翻訳しない特性は `translation` を持たない
- **特性の名前は、翻訳の有無によらずすべて書く。** トラッシュや場のポケモンを特性の名前で数える条件が、翻訳しないカードの特性を見るため
- **ワザの一覧は、翻訳しないカードにもすべて書く**(名前、必要なエネルギー、ダメージ)。ワザを使えるかの判定と、相手の場のダメージに足すダメージに使う
- **効果の中の選択は記法に書かない。** 何を選ぶか、誰につけるか、使うかどうかはプレイングの判断基準が決める。記法には候補の条件と上限だけを書く
- **山札の上から見て選ぶ操作の最小の枚数(`minTakeCount`、`minAttachCount`)は、条件の付いた選び方なら 0、条件の無い「カードを選ぶ」なら 1 にする。** 公式 Q&A(検索語「上から 見て えらばない」)で、デリバードの「エナジープレゼント」はエネルギーを選ばなくてよく、スマホロトムなどは 1 枚以上選ぶと回答されている。山札から探す操作の最小の枚数は骨組みが同じ決まりで決める(設計文書「カードによらない実行の決まり」の 3)
- **ワザの「〜枚まで」は、最小の枚数(`minCount` など)を 0 にする。** ポケモンが使うワザで「〜まで」選ぶときは 1 枚も選ばなくてよい(上級プレイヤー用ルールガイドの D-05)。トレーナーズと特性の「〜まで」は 1 枚以上で、選べるものが無いと使えない。「1枚選び」のように「まで」の無い文は、選べるものがあれば選ぶ
- **「シロナのポケモン」のようなトレーナーの名前のついたポケモンは、名前に文字列を含む条件(`nameIncludes`)で書く。** 拠り所は「ロケット団のポケモン」の公式 Q&A で、裁定のデータの書き方はシロナのガバイト(049093)の記録にある
- **コインで決まる効果は、条件ではなく操作の列の歩 `branchOnCoinFlip` か、つける枚数の上限 `AttachCount` で書く。** 条件は使えるかの判定でも評価され、判定の中で乱数を引いてしまうため(設計文書「順 6 で決めたこと(4 セッション目)」)。コインで決まるダメージの上乗せは、これまでどおり含めなかった効果に書く
- **翻訳に含めなかった効果は `excludedEffects` に理由とともに書く。** 理由は、相手の側に働く(`requiresOpponent`)、特殊状態(`specialCondition`)、回復(`healing`)、ダメージやダメカン(`damageOrDamageCounters`)、記録に持たない上乗せ(`damageBonusNotModeled`)、自分の次の番の制限(`ownNextTurnRestriction`)、後攻の最初の番に使えない制限(`firstTurnGoingSecondRestriction`)、一人回しでは使う理由が無い(`noReasonToUseInSoloPlay`)。計算の前提にそのまま出る。最大 HP を増やす効果は、場にある間ずっと働く効果の変える項目 `increaseMaxHp` で翻訳する(シロナのパワーウエイトの記録が例)
- **対戦風の一人回しのルール(設計文書「対戦風の一人回し(Issue 69)」)で書き分ける。** 相手のポケモン(バトル場でもベンチでも)に与えるダメージとのせるダメカンは `addDamageToOpponentField` で相手の場のダメージに足す(ダメカン 1 個 = 10。相手のどのポケモンに与えるかは書かない)。自分のポケモンのダメカンを相手にのせ替える効果は `moveDamageCountersToOpponentField`、自身をきぜつさせる効果は `knockOutSelf`。相手の属性(タイプ、ポケモンex などのルール、進化の段階、弱点、抵抗力、HP)で決まる効果と、相手の手札・山札・ベンチ・スタジアムに働く効果は、`requiresOpponent` で含めなかった効果に書く。相手のポケモンの数で量が決まる効果(「相手のポケモン全員に」など)は扱いを決めていないので含めず、判断を PR に書く
- **見直した日を入れる。** 対戦風の一人回しのルールで記録を見直したら、効果が変わらなくても `battleStyleSoloPlayReviewedOn` に見直した日(詳細ページを読み直した日。`verifiedOn` と同じ日)を入れる。新しく書く記録も同じルールで書くので入れる。見直していない記録には入れない

ワザのダメージ:

- ダメージの無いワザは `{ "kind": "none" }`、数値のワザは `fixed`。「50×」のように自分の側の数で決まるものは上乗せ `bonus` で書く(`perCount`: 数える対象 × 単位。`whenCountAtLeast`: 数える対象が N 以上なら M を足す)
- コイン、相手の側、追加のコストで決まる上乗せは持たず、含めなかった効果に書く。「おたがいの〜の数」のように相手の側を含む数も持たない。相手のポケモンのダメカンの数で決まる上乗せも持たない(相手の場のダメージを相手のポケモンのダメカンとして読む扱いは決めていない)。自分のポケモンのダメカンの数は数える対象 `damageCountersOnOwnPokemon` で数える(シロナのミカルゲの記録が例)
- 自分の側の数で決まる上乗せで、数える対象がまだ無いもの(ベンチの数、場のたねポケモンの数、ワザを使うポケモンのエネルギーの数など)は、計算に関係ないカードでも「部品を足す手順」で数える対象を足して持つ。ダメージは相手の場のダメージに足すため
- 効果の文でダメージを与えるワザ(ダメージの欄が空欄)は、効果の文の数値を固定のダメージとして持つ
- **ほかのカードがワザのダメージを増やす効果(グッズ、サポート、特性、どうぐ)は、「ダメージだけ」「相手が要る」として外さない。** 増やす量が自分の側だけで決まるなら、相手の場のダメージに足す量を増やすので翻訳する(この番だけのものは `increaseAttackDamageThisTurn`、場にある間ずっと働くものは変える項目 `increaseAttackDamage`。パワープロテインとシロナのロズレイドの記録が例)。条件はワザを使うポケモンに当たる。相手のポケモンの種類(ポケモンex など)で決まるものだけを `requiresOpponent` にする。棚卸しの一覧の根拠が「ダメージだけで、相手が要る」でも、この区別で確かめ直す(設計文書「順 6 で決めたこと(2 セッション目)」の「ワザのダメージを増やす効果」)

### 6. 記法に部品が無ければ足す

既にある部品で書けないときだけ、設計文書「部品を足す手順」に従って部品を足す。条件やきっかけの組み合わせで書けるなら足さない。部品を足したら、スキーマ(`card-record-schema.ts`)、部品ごとの処理の表(`effect-operations.ts` の `operationRunners` と `firstStepTargetChecks`、`conditions.ts` の `conditionEvaluators` など)、骨組みのテスト、設計文書の表を同じ変更で直す。既にある部品の欄を変えたら、その部品を使う既存の記録も直す。

### 7. 整形して、入口と JSON Schema を生成し直す

Biome は JSON の記録も整形するので、書いた記録はまずリポジトリの最上位で整える。

```bash
bun run lint:fix
```

続いてパッケージのディレクトリ(`packages/solo-play-simulator`)で入口 `src/card-record-table.ts` と JSON Schema `src/card-records/card-record.schema.json` を作り直す。記録を足したとき、記法のスキーマを変えたときは必ず実行する(最新かはテストが検査する)。生成したファイルには生成の中で Biome がかかる。

```bash
bun run generate:card-record-files
```

### 8. 翻訳ごとのテストを書く

翻訳あり(`translated`)の記録は、すべて `src/card-records.test.ts` に骨組みで実行するテストを持つ(無いと「翻訳ごとのテスト」のテストが落ちる)。`describeTranslation("<カード名>", ...)` の中で(名前が同じ翻訳が複数あるカードは `describeTranslation("ピカチュウ(050635)", ...)` のように先頭のカード ID を添える)、`card-test-support.ts` の `buildState` で小さな場を組み、効果を実行して場の動きを確かめる。

- 効果が起きること(引いた枚数、手札やトラッシュに移ったカード、ついたエネルギー、進化、ベンチの数)
- 使える条件と上限(条件を満たさないと使えない、上限を超えて選べない、0 枚でもよい)
- 裁定のデータに書いた解釈(解釈どおりに動くこと)
- コインで決まる効果は、`buildState` の `random` に並びの順に値を返す乱数を渡し、オモテとウラの両方を確かめる(既定の乱数は常に 0 でオモテになる)

### 9. 検査を通す

リポジトリの最上位で次を実行し、すべて通ることを確かめる。CI でも同じ検査が走る。

```bash
bun run test
```

```bash
bun run typecheck
```

```bash
bun run lint
```

```bash
bun run analyze
```

デッキ全体の記録がそろったら、そのデッキを記録だけで組み立てて回すテスト(`src/recorded-decks.test.ts`)にデッキを足し、手を選ばず順に使う手順と乱数で選ぶ手順で、勝敗まで回ることを確かめる。基本ルールに反する翻訳は、ここで見つかる。60 枚の内容は `src/recorded-decks.ts` に置く。リポジトリに置いてよいのは持ち主の許可があるデッキだけで、環境デッキなど大会で結果を残したデッキの 60 枚の内容は置かない([docs/pokemon-tcg/metagame-lookup.md](../../../docs/pokemon-tcg/metagame-lookup.md)「デッキ内容を保存しない」)。置けないデッキは、同じ手順を作業領域で回して確かめ、結果だけを PR に書く。Issue 22 のドラパルトex は、公式の記事で公開された優勝デッキを検証用に置くと決めた例外([docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md)「公式サイトの内容を転載しない方針との整理」)。

記録を書き終えたら、取得した詳細ページと記録の属性(名前、進化の段階と進化前、HP、タイプ、にげるエネルギー、ワザの名前・必要なエネルギー・ダメージ、特性の名前、ポケモンex・メガシンカex、テラスタル、トレーナーズの種類)を機械的に突き合わせる。写し間違いは検査では見つからない(スキーマに合った誤りの値は通る)。突き合わせの道具は作業領域に書いて捨て、ページの内容はリポジトリに保存しない。

### 10. 記録に残す

- 部品を足したとき、骨組みの決まりを変えたとき、分類を変えたときは、設計文書とその作業の Issue の決定事項(または PR の本文)に理由を残す
- 記録は公式の内容を読んで計算用に翻訳した結果であり、カードテキストやカード画像は記録にも文書にも保存しない
