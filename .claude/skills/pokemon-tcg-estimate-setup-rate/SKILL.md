# 主軸の成立率を計算する

デッキの主軸が何番目の番までに立つか、主軸のワザを何番目の番までに打てるかを、乱数試行(手札を配り、宣言した狙いの成立確率を最大にする手を探索で選んで番を進め、成立した割合を数える)で求める。設計の理由は [docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md) にある。用語は [CONTEXT.md](../../../CONTEXT.md)「デッキ診断」の節に従う。

## いつ使うか

- 「3 番目の番までに〜を打てる確率は」のように、番と動きを指定した質問に数字で答えるとき
- デッキ診断(`pokemon-tcg-diagnose-deck`)で「このカードを減らしても大丈夫か」に、カードテキストからの理屈だけでなく数字を添えるとき
- 新規構築(`pokemon-tcg-build-deck`)で、候補の枚数配分を比べるとき

次の質問には使わない。相手の行動を含めた計算はこの道具の範囲の外にある([docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md)「扱わないと決めたこと」)。

- 相手の妨害を受けた後の成立率、対戦相手ごとの勝率
- 4 番目の番より後の動き(終盤の動きは山札の残りと相手の行動に強く依存する)

## 道具の構成

| 部分 | 置き場所 | 中身 |
| --- | --- | --- |
| 計算の骨組み | `packages/solo-play-simulator/src/` | 山札を混ぜて配る、サイドを置く、先攻・後攻で番を進める、基本ルールの制限、効果の記法の部品の実行、宣言から狙いを導く処理、探索、乱数試行、締め切りごとの集計、枚数を変えたときの比較 |
| カードの記録 | `packages/solo-play-simulator/src/card-records/` | カード 1 種の属性、ワザと特性の一覧、効果の翻訳、裁定のデータ、含めなかった効果。全デッキで共有し、`pokemon-tcg-translate-card-effects` スキルの手順で書く |
| 入口 | `packages/solo-play-simulator/scripts/estimate-setup-rate.ts` | `bun run estimate:setup-rate <入力の JSON> [試行回数] [乱数の種]`。入力の JSON(デッキコード、60 枚の内容、宣言、変更案)を読み、計算の前提、成立率の表、失敗の要因の内訳、変更案の比較を出す |
| 入力の JSON | 作業領域(リポジトリの外) | デッキごとに書く。利用者のデッキの内容は本人のものなので、リポジトリに置かない |

デッキごとに書くのは宣言だけで、カードの効果と行動の選び方は書かない。カードの効果はカードの記録から、行動は探索から来る。

## 手順

### 1. デッキを読む

[docs/pokemon-tcg/deck-tool.md](../../../docs/pokemon-tcg/deck-tool.md) 手順 1 に従い、デッキコードから 60 枚の内容(カード名、カード ID、枚数)を読み取る。カード ID は印刷ごとに違うため、デッキに入っている印刷の ID をそのまま控える。合計が 60 枚であることを数える。

### 2. 全カードの 3 点確認をする

[docs/pokemon-tcg/card-lookup.md](../../../docs/pokemon-tcg/card-lookup.md) に従い、全カードの詳細ページを開いて効果を読む。宣言に書く主軸のワザの名前と主軸への道は、ここで読んだ内容に限る。記憶で書かない。同じ日に確認済みのカード ID は開き直さない([docs/pokemon-tcg/site-usage-notes.md](../../../docs/pokemon-tcg/site-usage-notes.md)「過度な連続アクセスをしない」)。

### 3. カードの記録の有無を確かめる

記録はどの印刷のカード ID からも引ける(`packages/solo-play-simulator/src/card-record-table.ts` の `cardRecordTable`)。記録の無いカード ID がデッキにあると、入口は計算せずに足りないカード ID をすべて示して止まる(`MissingCardRecordsError`)。

- 記録が無いカード ID は、`pokemon-tcg-translate-card-effects` スキルの手順で記録を書き(同じ名前の記録があって印刷の ID だけが無いときは、詳細ページを見比べて `cardIds` に足す)、`bun run generate:card-record-files` で入口と JSON Schema を生成し直してから、この手順に戻る
- 記録はあるが効果の翻訳が無いカード(書けない、計算に関係ない)や、翻訳に含めなかった効果があるカードは、そのまま計算できる。効果なし扱いになることが計算の前提に出る(手順 7)

### 4. 狙いを決めて宣言を書く

ユーザーの言葉で「何番目の番までに何ができていればよいか」を確かめ、宣言にする。宣言の書式(JSON)と欄の意味は [docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md)「宣言の書式」にある。狙いの 3 段(主軸が立つ、主軸のワザを打てる、N 以上で打てる)は、宣言とカードの記録から骨組みが導く。

- **`mainAttacks`**: 主軸のポケモンのカード ID と、ワザの名前(手順 2 で読んだ記録のワザの一覧の名前)。「X か Y のどちらかのワザ」のように、どれか 1 つが成り立てばよい主軸は並べて書く
- **`minimumDamage`**: 3 段目「N 以上で打てる」の N。ユーザーの言葉に無ければ省略する(狙いは 2 段まで)。N に要るエネルギーの数は書かず、記録のダメージの規則から骨組みが求める
- **`pathsToMainAttacker`**: 主軸への道。デッキ診断の主軸への道(スタジアムの効果で山札から進化させる道、ふしぎなアメの道、素の進化の道、など)をそのまま、道ごとに必要なカードのカード ID と置き場所(`hand`、`inPlay`、`inPlaySincePreviousTurn`、`stadium`、`deck`)で書く。探索はこの道の揃い具合を評価に使い、失敗の要因もこの道から作る。道の書き漏れは探索の判断と要因の両方に出るため、進化の元は `inPlaySincePreviousTurn`(前の番から場にいる)、手札から使うカードは `hand`、山札から持ってくるカードは `deck` と、カードの動きどおりに書く
- **`deadlines`**: 省略すると 2 番目の番と 3 番目の番。締め切りを 3 番目だけにすると、序盤を速くするカードの価値が数字に出ない(`pokemon-tcg-diagnose-deck` スキル「成立率を数字で示すとき」)

3 段に収まらない狙い(特定のポケモンが場にいる、トラッシュに N 枚集める、など)は宣言に書けない。そのまま伝え、近い形の狙い(そのポケモンを主軸にした宣言、上乗せの条件をダメージの下限で表す、など)で代えられるかをユーザーと確かめる。

### 5. 入力の JSON を作業領域に書く

1 つのファイルに、デッキコード、呼び名、60 枚の内容、宣言、比べたい変更案(任意)を書く。書式は `scripts/estimate-setup-rate.ts` の `EstimateInputSchema` にある。

```json
{
  "deckCode": "xG8Kax-DHob4e-84xcca",
  "name": "メガサーナイトex",
  "decklist": [{ "cardId": "048464", "count": 3 }, { "cardId": "049715", "count": 3 }],
  "declaration": {
    "mainAttacks": [{ "cardId": "048464", "attackName": "メガシンフォニア" }],
    "minimumDamage": 300,
    "pathsToMainAttacker": [
      {
        "name": "素の進化の道",
        "requiredCards": [
          { "cardId": "049715", "place": "inPlaySincePreviousTurn" },
          { "cardId": "048464", "place": "hand" }
        ]
      }
    ]
  },
  "variants": [{ "label": "キルリア 3→2(基本超エネルギー +1)", "changes": { "049715": -1, "049463": 1 } }]
}
```

- `decklist` は 60 枚全部を書く(上の例は抜粋)。合計が 60 枚でなければ入口が止まる
- `variants` の `changes` はカード ID → 増減枚数で、合計を 0 にする(合計が違えば入口が止まる)。抜いた枚数を何で埋めるかはユーザーと決め、決めていなければ基本エネルギー 1 枚で埋める(Issue 22 の比較と同じ)。ラベルには変更の前後の枚数と埋めたカードを書く
- ファイルは作業領域(scratchpad)に置き、リポジトリに入れない。会話が終わったら捨てる

### 6. 実行する

パッケージのディレクトリで実行する。

```bash
cd packages/solo-play-simulator && bun run estimate:setup-rate <入力の JSON のパス> 20000
```

- 先に試行回数を 200〜2,000 にして 1 回回し、記録の無いカード(手順 3)と宣言の誤り(記録に無いワザの名前、道の書き漏れ)を直してから、2 万回で回す。2 万回のとき、割合の揺れはおよそ ±0.7 ポイント(95 % の範囲)で、1 ポイント未満の差を意味のある差として語らない
- 所要時間の目安は、先攻・後攻 2 万回ずつで 1 デッキあたり 3〜8 分(開発責任者の Mac、Bun 1.4.2。[docs/solo-play-simulator-design.md](../../../docs/solo-play-simulator-design.md)「答え合わせ(Issue 27 の順 8)」の「回し方」)。変更案は 1 案ごとに同じ時間が加わるため、比べる案が多いときは背景で回し、ユーザーに見込みの時間を伝える
- 乱数の種は既定で固定されており、同じ入力なら同じ数字が出る。同じ種で回すので、変更案の差は試行の揺れではなく変更の効果として読める

### 7. 結果を読む

出力の順に読み、ユーザーに提示する前に次を確かめる。

- **計算の前提。** 効果を計算に含めていないカードに主軸への道のカードや主軸のワザに関わるカードが含まれていれば、その数字は主軸の成立率として使えない。記録を書く(手順 3)か、含めていないことを明示して提示する
- **失敗の要因の内訳。** 主軸が場にいない要因は「<主軸> が場にいない(<道の名前>: <足りないカード>(<今の置き場所>) が足りない)」の形で、宣言の道のうちいちばん揃っている道について出る。「道は揃っているが主軸が場にいない」が多いときは、道の書き漏れ(その道で主軸が立つのに必要なカードを書いていない)か、探索が道を使わなかった(評価の抜け)のどちらかで、宣言を見直してから提示する
- **探索の癖。** 探索は人が書いた手順より「打てる」「N 以上で打てる」を低く出す傾向がある(Issue 27 の順 8 の答え合わせ。直し方は Issue 51)。数字が実際のプレイヤーの感覚より低いときは、この点を提示に添える

### 8. 提示する

結果は次の順で示し、`pokemon-tcg-diagnose-deck` スキル「成立率を数字で示すとき」を守る。

1. 計算の前提(相手を含めない、手札の使い方は探索、先攻・後攻)。入口の出力の「計算の前提」をそのまま示す。カードごとの前提(効果を含めていないカード)は省かない
2. 狙いごとの成立率の表(先攻・後攻、2 番目と 3 番目の番)
3. 失敗の要因の内訳(上位のいくつか。道ごとにまとめてよい)
4. 枚数の変更案の比較。計算の範囲(3 番目の番まで)の外で価値を持つカードには、数字が低くても減らしてよい根拠にならないと添える
5. 提案の根拠が計算の結果なのか、カードテキストからの理屈なのか、ユーザーの実戦の経験なのかを区別して書く

### 9. 入力の JSON の扱い

入力の JSON には 60 枚の内容が入る。ユーザーのデッキの入力は、本人の許可が無い限りリポジトリに残さず、作業領域に書いて捨てる(デッキは本人のもの。[docs/deck-diagnosis-design.md](../../../docs/deck-diagnosis-design.md)「扱わないと決めたこと」)。許可があるとき、または公開されたデッキ(公式の記事に載った大会の優勝デッキなど)のときは、60 枚の内容と宣言を `packages/solo-play-simulator/src/issue22-decks.ts` や `src/additional-recorded-decks.ts` と同じ形で置き、記録だけで回すテスト(`src/recorded-decks.test.ts`)に足してよい。
