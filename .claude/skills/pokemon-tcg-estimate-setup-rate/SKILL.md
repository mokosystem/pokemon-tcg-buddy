# 主軸の成立率を計算する

デッキの主軸が何番目の番までに立つか、主軸のワザを何番目の番までに打てるかを、乱数試行(手札を配って固定の手順で番を進め、成立した割合を数える)で求める。設計の理由は [docs/setup-rate-design.md](../../../docs/setup-rate-design.md) にある。用語は [CONTEXT.md](../../../CONTEXT.md)「デッキ診断」の節に従う。

## いつ使うか

- 「3 番目の番までに〜を打てる確率は」のように、番と動きを指定した質問に数字で答えるとき
- デッキ診断(`pokemon-tcg-diagnose-deck`)で「このカードを減らしても大丈夫か」に、カードテキストからの理屈だけでなく数字を添えるとき
- 新規構築(`pokemon-tcg-build-deck`)で、候補の枚数配分を比べるとき

次の質問には使わない。相手の行動を含めた計算はこの道具の範囲の外にある([docs/setup-rate-design.md](../../../docs/setup-rate-design.md)「扱わないと決めたこと」)。

- 相手の妨害を受けた後の成立率、対戦相手ごとの勝率
- 4 番目の番より後の動き(終盤の動きは山札の残りと相手の行動に強く依存する)

## 道具の構成

| 部分 | 置き場所 | 中身 |
| --- | --- | --- |
| 計算の骨組み | `setup_rate/` | 山札を混ぜて配る、サイドを置く、先攻・後攻で番を進める、基本ルールの制限(最初の番、1 番に 1 回の制限、進化のタイミング)、乱数試行、締め切りごとの集計、枚数を変えたときの比較 |
| 規則ファイル | `setup_rate/decks/<名前>.py` | デッキごとに書く。カード表、60 枚の内容、対戦の準備、行動の並び(優先順位)、ワザの選び方、狙い、失敗の要因、枚数の変更案、前提 |

骨組みはデッキに依存しない。カードの効果を計算に落とす規則と番ごとの優先順位はカードテキストから機械的に作れないため、デッキごとに規則ファイルとして書く。

## 手順

### 1. デッキを読む

[docs/pokemon-tcg/deck-tool.md](../../../docs/pokemon-tcg/deck-tool.md) 手順 1 に従い、デッキコードから 60 枚の内容(カード名、カード ID、枚数)を読み取る。

### 2. 全カードの 3 点確認をする

[docs/pokemon-tcg/card-lookup.md](../../../docs/pokemon-tcg/card-lookup.md) に従い、全カードの詳細ページを開いて効果を読む。規則ファイルに書く効果は、ここで読んだ内容に限る。記憶で書かない。同じ日に確認済みのカード ID は開き直さない([docs/pokemon-tcg/site-usage-notes.md](../../../docs/pokemon-tcg/site-usage-notes.md)「過度な連続アクセスをしない」)。

### 3. 狙いを決める

ユーザーの言葉で「何番目の番までに何ができていればよいか」を確かめ、次の 3 段に分けて狙いにする。

1. 主軸が立つ(例: メガサーナイトex が場にいる)
2. 主軸のワザを打てる(例: メガシンフォニアを打てる)
3. 上乗せの条件(例: 300 以上で打てる、トラッシュに 4 枚ある)

締め切りは 2 番目の番と 3 番目の番の両方に置く。締め切りを 3 番目だけにすると、序盤を速くするカードの価値が数字に出ない(`pokemon-tcg-diagnose-deck` スキル「成立率を数字で示すとき」)。

狙いが進化ではない形(何番目の番にワザを打つ、トラッシュに何枚集める、など)でも同じ骨組みで書ける。既存の規則ファイルの中から狙いの形が近いものをひな型にする。

| ひな型 | 狙いの形 |
| --- | --- |
| `mega_gardevoir_ex.py` | 2 進化の主軸をスタジアムとふしぎなアメで立て、ワザでベンチにエネルギーを配る |
| `mega_charizard_ex.py` | 後攻 1 番目の番に特性で出したポケモンのワザを打つ。番の終わりにトラッシュする特殊エネルギー |
| `bakegakure.py` | トラッシュに特定のポケモンを N 枚集める。特性で山札に戻るポケモン |
| `dragapult_ex.py` | 2 進化の主軸に 2 種類のタイプのエネルギーをつける。山札からエネルギーをつけるサポート |

### 4. 規則ファイルを書く

`setup_rate/decks/` に新しいファイルを作り、ひな型を写して書き換える。書く項目と注意は次の通り。

- **カード表**: カード名、カード ID、種別、たね・1 進化・2 進化、HP、タイプ、進化前、ルールを持つポケモンか、にげるエネルギー。効果の文章はここに書かない
- **60 枚の内容**: 手順 1 で読んだ通りに。合計が 60 になることをテストが確かめる
- **対戦の準備**: バトル場に置く優先順位と、ベンチに出すポケモン。特性を使いたいポケモン(手札から出したときの特性など)は手札に残す
- **行動の並び**: 優先順位の高い順に `Action` を並べる。骨組みは、実行できる行動のうち最も上のものを 1 つ実行し、また最初から探す。これを実行できる行動が無くなるまで繰り返す
- **効果の書き下し**: 各行動の docstring に、公式の詳細ページで確認した効果を自分の言葉で書く。カードテキストを引き写さない
- **ワザの選び方**: 番の終わりにどのワザを使うか
- **狙い**: 番の終わり(ワザを使う前)の場を見て真偽を返す関数。「打てる」は、バトル場からそのワザを使える状態で、先攻の最初の番は偽
- **失敗の要因**: 締め切りの番に狙いが成立していない理由を短い言葉で返す。事後分析なのでサイドの中身を見てよい
- **枚数の変更案**: 比較したい増減を `Variant` で並べる。合計は 60 のまま
- **前提**: 相手を含めないこと、固定した手順、対戦の準備の置き方、使わないワザや特性を列挙する。出力の先頭に印字される

判断には `count_unseen`(山札とサイドの合計)を使い、`count_in_deck`(山札だけ)を使わない。プレイヤーは山札とサイドのどちらにあるかを知らない。山札を見てよいのは、検索の効果を実行するときと、失敗の要因の事後分析だけ。

骨組みに無い操作(番の終わりの処理、山札の上を見る、場のポケモンを山札に戻す、など)が要るときは `setup_rate/state.py` に基本操作を足し、理由を [docs/setup-rate-design.md](../../../docs/setup-rate-design.md)「骨組みに手を入れた記録」に書く。

### 5. 実行して規則を検査する

```bash
uv run python -m setup_rate <名前> --trace
```

先攻・後攻それぞれ 1 回の対戦の行動の履歴が出る。次の書き誤りを探し、直す。

- 特性を使えるポケモンを、特性を使わずに出している
- エネルギーを、進化させる前の別のポケモンにつけている
- 手札の進化カードを使えるのに、山札から別の線を作っている
- 山札から探す手段があるのに、探す相手の一覧に入っていない
- バトル場に出せないままワザを打てる状態を逃している(にげるエネルギー、入れ替えの手段)

失敗の要因の内訳が大きい項目について、その要因で失敗した対戦の履歴を数件読む。規則の書き誤りなら直し、デッキの性質なら前提に書く。

```bash
uv run python -m unittest discover -s tests
```

テストは、骨組みが基本ルールを守ること、各規則ファイルが 60 枚で最後まで走ることを確かめる。新しい規則ファイルは `tests/test_deck_rules.py` の一覧に加える。

### 6. 試行を回す

```bash
uv run python -m setup_rate <名前> --trials 20000
uv run python -m setup_rate <名前> --trials 20000 --compare
```

同じ乱数の種で回すので、枚数の変更案の差は試行の揺れではなく変更の効果として読める。試行回数が 20000 回のとき、割合の揺れはおよそ ±0.7 ポイント(95 % の範囲)なので、1 ポイント未満の差を意味のある差として語らない。

### 7. 提示する

結果は次の順で示し、`pokemon-tcg-diagnose-deck` スキル「成立率を数字で示すとき」を守る。

1. 前提(相手を含めない、固定の手順、先攻・後攻)。規則ファイルの前提をそのまま示す
2. 狙いごとの成立率の表(先攻・後攻、2 番目と 3 番目の番)
3. 失敗の要因の内訳
4. 枚数の変更案の比較。計算の範囲(3 番目の番まで)の外で価値を持つカードには、数字が低くても減らしてよい根拠にならないと添える
5. 提案の根拠が計算の結果なのか、カードテキストからの理屈なのか、ユーザーの実戦の経験なのかを区別して書く

### 8. 規則ファイルの扱い

規則ファイルには 60 枚の内容と、カードの効果を自分の言葉で書いた文が入る。ユーザーのデッキの規則ファイルは、本人の許可が無い限りリポジトリに残さず、作業領域に書いて捨てる(デッキは本人のもの。[docs/deck-diagnosis-design.md](../../../docs/deck-diagnosis-design.md)「扱わないと決めたこと」)。許可があるとき、または公開されたデッキ(公式の記事に載った大会の優勝デッキなど)のときは、動作確認用の例として `setup_rate/decks/` に置いてよい。ファイルの先頭にデッキコード、出典、確認日を書く。
