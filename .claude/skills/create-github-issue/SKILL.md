# GitHub Issue 作成ガイド

`gh` コマンドで GitHub Issue を起票・更新する。

## Issue を書く目的

Issue は **何のためにやるのかと、着手までに固まった決定を残す場**である。

未来の実装者（自分・他のメンバー・AI エージェント）が Issue を読むだけで「なぜやるのか」「何をもって完了とするのか」を判断できる状態にする。

## 目的を最初に書く（最重要）

**`## 目的` は起票の時点で必ず書く。** ここが空の Issue は起票しない。

- 何を達成したいのかを書く
- それができないと何が困るのかを書く
- **手段ではなく理由を書く。** 「デッキ検証機能を作る」は手段であって目的ではない。「レギュレーションで使えないカードを初心者に勧めない状態にしたい」が目的にあたる

目的が無いと、どの手段が最適かを判断できない。実装の途中で選択を迫られたとき、立ち返る先が無いまま手段を選ぶことになる。掘り下げも、目的が定まっていなければ何を問うべきかが決まらない。

## 完了の定義は着手前までに固める

**`## 完了の定義` は、着手する時点までに埋める。** 起票時に埋まっていなくてよい。

このリポジトリの Issue は、要件が固まりきる前に起票することが多い。着手前に完了条件を確定させる運用ではなく、掘り下げや調査を経て固めていく。そのため起票時は見出しだけ置き、決まった時点で埋める。

チェックボックス `- [ ]` で書くと、着手者がチェックを入れて進捗を表せる。

## 構成

節の構成は `.github/ISSUE_TEMPLATE/issue.md` が定義する。GitHub の画面から起票するとこのテンプレートが適用される。

`gh issue create --body-file` で本文を直接渡す場合はテンプレートが適用されないため、**そのファイルを読んで同じ構成に揃える**。構成をこのスキルにも書くと二重管理になり、いずれ食い違う。

| 節 | いつ書くか |
| --- | --- |
| `## 目的` | 起票時に必ず |
| `## 着手できない理由` | ブロッカーがあるときだけ |
| `## 完了の定義` | 着手する時点までに |
| `## 現時点の考え` | 任意 |
| `## 未確定` | 任意 |
| `## 決定事項` | 掘り下げや議論で固まったら追記する |

`目的` 以外は、該当が無ければ節ごと省いてよい。書くことが無いのに見出しだけ並べても読み手の負担が増えるだけである。

## 着手できない理由を隠さない

先行 Issue の未完了・権限の不足・仕様の未確定・外部サービスの待ちなど、**今すぐ着手できない事情があるなら書く**。あわせて **何が起きれば解消するのか** も書く。

解消条件が無いと、いつ再開できるのかを誰も判断できない。ブロッカーだけ書いて放置された Issue は、読んだ人が毎回同じ調査をやり直すことになる。

解消したら、この節ごと消して着手できる状態に整える。

ブロッカーが無いときは節を置かない。「なし」と書いた行が並ぶより、無いことが一目で分かるほうがよい。

## 書きすぎない

要件が変わる前提の Issue に、実装の詳細を先に書き込まない。書いた分だけ、変わったときに直す手間と、古い記述が残るリスクが増える。

現時点で決まっていないことは「未確定」に論点として置き、決まってから「決定事項」に移す。

## 更新する

議論や調査で何かが決まったら、Issue 本文に追記する。コメントに書くだけで本文を放置しない。後から読む人は本文しか読まないことがある。

```bash
gh issue edit <番号> --body-file <path>
```

経緯を残したい場合はコメントを使う。本文には結論を、コメントには経緯を置く。

```bash
gh issue comment <番号> --body-file <path>
```

## 投稿方法

本文に Markdown のコードブロック（バッククォート 3 つ）が含まれる場合は、**`--body-file` を使う**。ヒアドキュメントではシェルがバッククォートをコマンド置換として解釈し、投稿された本文でコードブロックが壊れる。

```bash
gh issue create --title "<タイトル>" --body-file <path>
```

投稿後にレンダリングを確認する。

```bash
gh issue view <番号> --json body --jq '.body'
```

崩れていたら `gh issue edit <番号> --body-file <path>` で入れ直す。

## タイトル

- 日本語で、何をするのかを端的に書く
- 「〜する」の形にする（例: `公式カード検索の参照手順書を追加する`）
