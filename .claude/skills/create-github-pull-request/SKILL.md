# GitHub Pull Request 作成ガイド

`gh` コマンドで PR を作成・更新する。

## PR を書く目的（常に立ち返ること）

説明欄を書くときは、次の 2 つを判断の基準にする。テンプレートを機械的に埋めない。

### 1. 未来の開発者が、設計理由と実装の意図を理解できるか

PR は **コードに残らない意思決定の記録**である。

コードからは何をしたか（What）が読み取れる。なぜそうしたか（Why）と、他にどんな選択肢があってなぜ採らなかったか（Why not）は、PR にしか残らない。数か月後の自分や他のメンバー、AI エージェントが履歴を辿ったときに、実装がその形になっている理由を追える必要がある。

### 2. レビュアーの視点で書けているか

レビュアーは PR を**初見で読む**。コミットを順に追うとは限らず、Issue の経緯を把握しているとも限らない。背景 → 範囲 → 判断の根拠、の順に説明する。

動作確認をレビュアーに委ねない。確認は PR を出す側の責任で終わらせ、レビュアーには**設計判断の妥当性を議論してもらう**。

### 迷ったら問い直す

- 半年後の自分が読んで、なぜこの実装なのか分かるか
- 初見のレビュアーが、5 分で文脈を掴めるか

どちらかが NO なら、情報が足りないか書き方が適切でない。

## 説明欄の構成

節の構成は `.github/PULL_REQUEST_TEMPLATE.md` が定義する。GitHub の画面から作るとこのテンプレートが本文に入る。

`gh pr create --body-file` で本文を直接渡す場合はテンプレートが適用されないため、**そのファイルを読んで同じ構成に揃える**。構成をこのスキルにも書くと二重管理になり、いずれ食い違う。

各節に何を書くかは以下に示す。テンプレート内のコメントはその要約である。

該当が無い節は、省略せず理由を添えて「なし」と書く。丸ごと省くと、書き忘れなのか該当なしなのかをレビュアーが判別できない。

### 対応する Issue

対応する Issue の番号または URL を書く。

`Closes #<番号>` のような自動クローズ用の記法は使わない。1 つの Issue が 1 つの PR で完結するとは限らず、残作業があっても機械的に閉じてしまう。Issue を閉じるかどうかは人が判断する。

### 対応する範囲 / 対応しない範囲

**対応しない範囲を積極的に書く。** 範囲を明示するとレビューの観点が定まり、別 PR で扱う事項も共有できる。

### 変更点概要

3 つに分ける。

1. **なぜこの変更が必要か** — 背景と動機。Issue の目的を引用すると伝わりやすい
2. **主な変更内容** — 変更したファイルと、その内容
3. **なぜこの実装にしたか** — 設計判断の根拠。論点ごとに小見出しを立てる。採らなかった案があれば、それも理由とともに書く

### 動作確認

**CI で分かることは書かない。** lint・型検査・テスト・ビルドが通っているかは CI の結果を見れば分かる。PR 本文に書くとノイズになる。

書くのは **CI では分からないこと**である。

- 画面や外部サイトに関わる変更なら、実際に開いて何を確認したか
- 実際に操作して確かめた挙動
- 手元でしか再現できない検証

確認していないことを確認したように書かない。実行できなかった検証があれば、その旨を明記する。

### レビュアーに見てほしい点

コードレビューは設計判断を議論する場であり、動作確認やバグ探しを委ねる場ではない。

- 「〜が正しく動くか」「〜にバグがないか」という書き方はしない
- 判断に迷った箇所、トレードオフのある選択、規約の解釈が分かれる箇所を挙げる
- 「XX を採用したが妥当か」「複数案のうち YY を選んだ。別の観点があれば指摘してほしい」の形で書く

### 補足情報

関連する設計資料、関連 Issue、この PR では対応しない既存の課題（別 Issue があれば番号）などを書く。

## 書いてはいけない情報

- **CI で分かる情報**（検査コマンドの通過、テスト件数、変更ファイル数）
- **差分を見れば分かる説明**。何を変えたかの言い換えで終わらせず、なぜ必要だったかを書く
- **コミットメッセージのコピー**
- `Closes` / `fixes` などの自動クローズ記法
- レビュアーへの動作確認の依頼

## タイトル

- 日本語で、変更内容を端的に表す
- 「〜する」の形にする（例: `公式カード検索の参照手順書を追加する`）
- Issue 番号は付けない。本文の「対応する Issue」で紐づける

## 投稿方法

本文に Markdown のコードブロック（バッククォート 3 つ）が含まれる場合は、**`--body-file` を使う**。ヒアドキュメントではシェルがバッククォートをコマンド置換として解釈し、投稿された本文でコードブロックが壊れる。

```bash
gh pr create --base main --title "<タイトル>" --body-file <path>
```

投稿後にレンダリングを確認する。

```bash
gh pr view <番号> --json body --jq '.body'
```

崩れていたら `gh pr edit <番号> --body-file <path>` で入れ直す。

## 作成前の確認

現在のブランチを確認する。

```bash
git rev-parse --abbrev-ref HEAD
```

`main` に居る場合は、ブランチを切り忘れている可能性が高い。そのまま PR を作らず、ユーザーに確認する。

## 実行ポリシー

PR 作成の依頼は、その前提となるコミットとプッシュの依頼を含む。判定は `create-git-commit` スキルの実行ポリシーで行い、ここでは再定義しない。

`--draft` を付けるかはユーザーの指示に従う。指示が無ければ通常の PR として作成する。
